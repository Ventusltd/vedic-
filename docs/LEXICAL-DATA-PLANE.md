## Lexical scope
Index eligible public estate function identifiers, committed documentation, public issue/PR/Neural Link records and commit messages when accessible and authorised for public use. Private chats are not automatically accessible or eligible. Do not ingest private repositories, personal data or secrets into public output. Record coverage/exclusions/failed sources/checkpoints. Preserve raw spelling, exact source range and UTC provenance. Search normalisation (Unicode NFC, casefold, optional camel/snake segmentation) is not semantic equivalence. Mention, declaration, dependency and tested invocation are separate kinds of evidence.

## Data grains and keys
- word: one normalised lexical form per versioned normalisation policy; search key, not meaning identity.
- mention: one source occurrence keyed by source kind + stable source locator/revision + start/end offsets + normalisation policy. Git records carry repo/commit/path/blob; issues/comments carry immutable provider ID and version/content hash. Retain exact spelling, observed timestamp and evidence scope. Deduplicate historical copies separately from preserving occurrence provenance.
- function occurrence: existing Modular Star repo+commit+path+tablet+element+span/columns (as resolved); no new producer IDs. Distinguish observed historical and active scan membership.
- word-family candidate: word + existing Stars family/element identity + explicit association basis, with source evidence; association not a semantic verdict.
- dictionary sense: VEDIC permanent ID, original allocation timestamp, unique meaning key, versioned contracts, aliases, evidence and demo references; repeated words allowed, missing identity null.
- relationship: stable source and target identities + relation type + evidence locator/hash; do not infer a call from a reference or equivalence from repeated spelling.
- composition: existing VEDIC IDs and pinned contract versions in explicit ordered graph; typed ports, units, proof and demo. Each valid new meaning is eligible for a separately allocated ID.
- proof/demo receipt: executable ID, exact input/output fixture hash, code/contract revision, test environment, status and UTC; one observed assertion per receipt.

## Discovery and lifecycle
Start with the existing Stars tablet_element/name + element/family + occurrence join (historical and active scopes explicitly separate). Group by normalised word; prioritize COUNT(DISTINCT family_id)>1, COUNT(DISTINCT repo/path)>1, or multiple independently evidenced Spider contexts. Separate multiple meanings from the same function reused across areas. Same family may have multiple uses; same name may identify different families; neither condition alone proves multiple semantic senses. Use an explicit curated review queue, not automatic VEDIC allocation or code execution. Later add authorised documentation/issue/commit text incrementally, with evidence-backed term-to-family candidates; only index observed data. Report candidate counts, distinct families, distinct areas, reviewed senses and tested demos separately. No double counting by repeated commit, nested span or alias. Preserve the three identities: Git, Modular Star, VEDIC.

## Storage and processing
Python producer consumes verified existing snapshots. DuckDB local queries over immutable ZSTD Parquet partitions; separate occurrence/evidence, word-family candidates, curated senses, relationship, proof and composition tables. Use snapshot ID and source-kind partition strategy only after measuring row distribution; don't partition per word. Keep canonical VEDIC registry as append-only Git data, Parquet derived, not a competing identity allocator. Use one acquisition per input digest, snapshot manifest with hashes, schema version, source coverage and explicit times. One-time backfill distinct from incremental new/changed source processing; preserve earlier snapshots. Idempotent rebuild on same inputs; verify source hashes, row/distinct key equality, null keys, referential integrity and semantic review states. Rebuild/reconcile changed source versions without overwriting historical evidence. Stage outputs atomically, retain prior good version on failures. Do not publish raw corpus or private evidence. Pin DuckDB/Python dependencies after reuse review; no database service required for read-only local analytics. Use existing on-demand browser DuckDB only if measured useful; small JSON index for V1. No new ChatGPT schedule slots.
