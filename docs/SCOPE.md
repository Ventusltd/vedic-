# VEDIC — The Language of GlobalGrid2050
## Owner-directed development scope and operating charter
26 November 2026 | Lead: Tacit 1 | Coordination: Neural Link #87

### 1. Mission
Make existing software intelligence understandable and reusable by humans and AI. Translate what code achieves, rather than merely describing syntax. The owner has authorised a continuously expandable dictionary: functions, meaningful bodies, packages, workflows, application capabilities and validated compositions can all become entries. New combinations may themselves become building blocks for future combinations. Do not claim arbitrary combinations are meaningful or executable. The initial dashboard is a preview, not a completed translation of the producer-reported 477,785 unique numbered lines (Modular Star snapshot 25 Nov 22:43 UTC).

Use release assets modular.sqlite.gz and catalog.json.gz; mutable release tag is not an immutable pin. Reuse unpack(), rebuildTablet(), elementSource(), find-prior.mjs and existing permanent-number checks. Python adapters are read-only and require parity evidence.
- Periodic Table is the existing functional block catalogue; retain its permanent numbers, symbols and categories (e.g. Vg, Vn, Gc are distinct until evidence supports identity). Do not infer exact membership from matching names.

- Kuiper Belt is the estate navigation and evidence framework: a body should have an openable destination; a claim without a reproducible key is a candidate. Keep application/repository depth distinct from function depth. Do not duplicate its renderer, taxonomy or orbit calculations.

### 3. Permanent dictionary identity
Follow the REPD identity stability precedent GG2050-REPD-<Ref ID>, with a distinct VEDIC namespace GG2050-VEDIC-000001 onward. Numbers allocated once by Tacit 1's append-only registry; never recycle or reassign. Keep initial IDs 1–6. Preserve retired records with a tombstone/status, never silently delete. Version meaning/contracts, sources and demonstrations without replacing the stable identity. Substantively different capabilities or combinations receive new IDs. Equivalent aliases and multi-view representations point to the canonical entry; same source occurrence does not automatically prove semantic equivalence. VEDIC IDs do not substitute for existing Stars, REPD or Periodic Table identities. Validate stability against previous Git version; protect historical releases.

### 4. Language and data contract
Each entry should carry: gg_id; immutable registry key; shorthand word or phrase; plain-English purpose; kind (function/body/package/workflow/application/composition); inputs and outputs with types, units and bounds; triggering condition; limitations; dependency/component references and version pins; source repository/commit/path/blob/physical ranges and columns where available; original Stars line/element/family IDs when resolved; application/estate contexts; Periodic Table category and block; Vedic class; computer-science and maths discipline tags; evidence state; demonstration descriptor; proof receipts and date; supersession/retirement information; credits. Unknown remains null, never zero or pass. Current schema is a deliberately narrow six-entry seed; evolve additively, document migration, do not imply all these fields already exist. Separate curated candidate classification from exact producer membership. Distinguish manifest-declared, static source inference, historical, executed tested assertion, live verified and unknown; use separate axes where necessary. Source-reviewed text is not an executable language by itself.

### 5. Recursive composition / grammar
A composition is an ordered or explicitly parallel dependency graph of existing stable entries, with typed input/output ports, units, parameters, constraints, error behavior and source/test receipts. A successful composition can become a new dictionary word and be nested in later compositions. Detect cycles, missing dependencies, incompatible types/units, unsupported side effects, duplicate aliases and missing data. Preserve explicit order when relevant; distinguish a set of functions from an executable pipeline. Do not silently convert coordinate order, voltage units, power/energy, or distances. Require reproducible demo and appropriate tests before promoting executable status. Reuse existing code generator and Chemistry evidence before creating a new engine. The first ORIENT candidate combines existing MEASURE and BEARING functions on shared inputs; it is not turn-by-turn navigation or engineered routing. No claim of infinite valid combinations.

### 6. Demonstration law
Every entry must provide an openable demonstration link where feasible, or explicit reason why unavailable. Distinguish exact-source runnable demo; existing application example (not proof of exact function execution); historical example; static source/explanation; unavailable. A demonstration is not a proof of all real-world behavior. Use upstream implementation without rewriting maths, pin source and verify bytes, retain licence and NOTICE. Show example inputs, outputs, units and limits; accept safe editable inputs where appropriate. Avoid live private data, secrets, unapproved API calls or infrastructure access. Capture expected outputs and negative cases in Python-driven browser tests. A failed link is a measurable issue, not a silent success. Kuiper's openability principle applies to every entry.

### 12. Intentional ambiguity and the philosophy of inquiry
The owner intends VEDIC to have layered meaning and remain open to discovery. Express philosophical inspiration in secular, inclusive English, without religious names, doctrinal claims or assertions of authority in the public language. The following are design analogies, not scientific claims or a translation of a single doctrine.

- **Question before conclusion.** Explore several meanings, inspect counterexamples and ask what lies beneath an implementation. Search may resolve to many candidates; do not force one interpretation.
- **The whole and the parts.** A functional body can participate in many applications and combinations. Reveal underlying relationships and reusable principles without confusing analogy with verified equivalence.
- **Define through boundaries as well as purpose.** Explain what an entry does and what it does not establish. Preserve negative evidence and failed experiments.
- **One word, many contexts.** A shorthand may have several senses, aliases or candidate interpretations. Give distinct meanings stable identities and context; preserve relationships rather than erase differences. Search may be ambiguous; a selected executable reference, version, units, inputs, effects and test assertions must be unambiguous.
- **Knowledge is revisable.** Preserve open questions, competing hypotheses and alternative compositions. Distinguish candidate from evidence; refine the dictionary without erasing history.
- **Discovery and execution are separate.** Ambiguity is useful in exploration, metaphor and human-facing language; never use it to hide missing evidence, invent coverage or weaken deterministic validation. Resolve meanings before execution; if unresolved, show alternatives rather than guessing.

These principles supplement Sections 1–11. Keep public vocabulary plain English and welcoming to all backgrounds. Do not introduce religious nomenclature into classifications, UI, IDs or executable commands. Existing engineering provenance and exact source records remain intact. The dictionary permits repeated words with distinct permanent sense keys. Word labels are not unique identifiers. Every allocated meaning retains its GlobalGrid ID, original UTC creation timestamp and Git creation evidence permanently. Multiple entries allocated in one commit may share a timestamp; uniqueness belongs to the ID and canonical meaning key, not the clock. Preserve original source identities independently. Do not reset creation dates when revising a description or refreshing source evidence. A materially new meaning receives a new identity. Initial six allocations were recovered from commit 5ddc2e611dbcccb68cc4f7342637fddb912e5ef1 at 2026-11-26T01:35:15Z. The initial key scheme references canonical translation IDs or ordered composition IDs; exact semantic equivalence across distinct source references still requires evidence.

### 13. Three identities — the foundation of composition

The owner defines three complementary identity systems. Do not replace any with another:

| Identity | Question | Canonical evidence |
| --- | --- | --- |
| Git SHA | Which exact revision and bytes? | Repository, commit SHA, path, blob SHA and exact source span; retain immutable history. |
| Modular Star | Which numbered code constitutes this body, and where is it reused? | Existing permanent tablet, element, family and ordered line IDs, with verified occurrence and database snapshot. No new allocator; unresolved IDs remain null. |
| VEDIC | What does this mean, and how may it be combined? | Permanent GG2050-VEDIC ID, immutable creation timestamp, unique meaning key, versioned contract and demonstration/evidence. |

The three identities form an evidence-linked relationship, not a one-to-one mapping: one meaning can have several implementations; one body can support several meanings; a new Git revision need not imply a new meaning. Different words may reference a single meaning through aliases, and the same word may reference several distinct meanings. A materially new meaning or composition receives a new VEDIC ID; a refined description or proven implementation replacement does not erase history. Preserve all three provenance layers and their uncertainty. Kuiper's reproducible-key and openable-destination laws apply.

Recursive compositions reference existing VEDIC IDs and pinned contract versions; each component resolves to its existing Modular Star and Git evidence. Record the composition's own Git source and existing Modular Star IDs when indexed, not fabricated numbers. A tested composition may become a reusable word in later compositions. This supports an open-ended space of systems rather than a guarantee of infinitely many valid executable programs. Use existing Chemistry, Maths Genome, Periodic Table, code generator and CVAA checks for compatibility and proof. All three identities must be separately discoverable in the register; do not invent missing associations or claim exact runtime identity without evidence. Python validates references, typed ports, units, cycles, version compatibility, provenance and immutable identity; show unknowns honestly. Keep prior producer systems unchanged.

### 14. Owner scope boundary — two-dimensional dictionary and dashboard
VEDIC is a simple two-dimensional dashboard and dictionary, not a new cosmic visualisation, graph renderer, simulation platform, programming runtime or replacement for any existing estate system. The REPD-style searchable, sortable register is the primary interface. Each entry exposes its plain-English meaning, three identities, original timestamp, functional group, demonstration and evidence links. Multiple meanings of one word remain valid. Reuse existing demonstrations and link out to existing Spider, Spider Printer, Maths Genome, Periodic Table, Kuiper, Wafer, Cosmic, Furnace, Teleprinter and CVAA resources as appropriate; do not reproduce their interfaces in VEDIC. Parquet/DuckDB and Python are supporting data infrastructure, not additional products or an excuse for scope creep. Represent compositions as dictionary entries with references and proof; actual execution belongs to existing approved engines/demonstrations. This boundary takes precedence over broader interpretations of earlier sections. Prioritise a working V1 and incremental dictionary growth, with no new visualisation engine or upstream changes.

One architecture. Growing vocabulary. New combinations. Reproducible evidence. Live long and prosper. 🖖
